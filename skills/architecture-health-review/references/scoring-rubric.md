# 评分锚点、默认维度与置信度

## 0–5 锚点

「低分」不是失败测试的同义词，而是代码在变化、理解或恢复上已经产生结构性成本。

| 分 | 含义 |
| --- | --- |
| 5 | 模块深、知识集中、变化局部；有持续度量、复盘和自动约束证明这一状态 |
| 4 | 边界和约定系统化，常见变化可以局部完成；仍有少量已知债务 |
| 3 | 主路径可用，但存在重复规则、人工协调、浅接口或未收敛的跨模块依赖 |
| 2 | 已观察到结构性放大：同一规则在多个模块重复、调用链透传实现细节、一个小改动需要多处同步，或失败/权限语义由多个层共同决定；只能靠人工记忆或局部补丁维持 |
| 1 | 边界基本失效，调用者必须理解内部机制才能正确使用；关键变化无法局部实施，或恢复路径依赖临时操作 |
| 0 | 缺失、互相矛盾，或无法提供可信证据 |

**3/5 表示「能工作但有明显债务」，不是健康默认值。** 给 4–5 分需要反通胀门槛（见 SKILL.md §3）同时成立。

## 默认维度

项目自带评分协议时以项目为准；没有时用下面这六个维度作为默认，并按项目实际调整二级指标。

| 维度 | 权重 | 二级指标 |
| --- | ---: | --- |
| 复杂性控制 | 20 | 变化放大 8、认知负荷 7、特例与信息泄漏 5 |
| 模块深度与边界 | 20 | 接口成本/隐藏收益 7、信息隐藏 6、层次错位 4、耦合与透传 3 |
| 演化式设计 | 15 | 结构不同的候选方案 5、增量与回退 5、持续重构 5 |
| 战略执行 | 15 | 设计投资与债务偿还 6、路线与依赖一致性 5、变更局部性 4 |
| 一致性与显然性 | 15 | 领域术语/文档 5、契约与非显然注释 3、代码语义一致性 4、自动化约束 3 |
| 证据、反馈与恢复 | 15 | 未知发现 5、失败/权限/恢复测试 5、CI/观测/回退 5 |

计分方式：维度得分 = Σ（二级指标权重 × 指标得分 / 5）；总分 = 六个维度得分之和（满分 100）。

如果项目需要**两个**评分对象（例如子系统内部健康度 + 与宿主仓库的契合度），用同一套权重分别评，报告时保留两个原始分数——合成一个仪表盘分会让人分不清问题出在哪一侧。

## 健康等级

| 分数 | 含义 |
| --- | --- |
| 80–100 | 健康，可持续扩展 |
| 60–79 | 可持续开发，但存在明确治理债务 |
| 40–59 | 脆弱，应先治理再扩展 |
| 0–39 | 高风险，需要优先恢复边界、验证和反馈能力 |

**任一关键维度低于 2/5，必须单独列为阻断风险，不能被总分掩盖。** 一个 82 分但有一维 1/5 的系统，不是健康系统。

## 置信度

| 级 | 依据 |
| --- | --- |
| A | 主要结论由自动化测试、CI 或可复现运行结果支持 |
| B | 主要结论由代码抽样、文档与部分自动验证支持 |
| C | 主要依赖设计意图、个人判断或尚未验证的假设 |

整体置信度不是简单平均。只要关键维度仍缺少证据，整体置信度最多为 `B`；多个关键维度缺少证据时标为 `C`。

## 「未知的未知」

不直接评分。它通过以下方面间接评估：

- 未知发现速度（新问题多久能暴露）
- 失败诊断（出错时能否定位到原因）
- 可观测性（运行状态是否可看）
- 回退能力（出事能否安全退回）
- 关键假设的验证程度

## 评分卡模板

```text
评分对象：
阶段：设计期 / 实现后 / 合并前
Git SHA：
范围：
验证命令：

维度 | 二级指标 | 0–5 分 | 证据路径 | 置信度 | 与上次差值 | 改进动作
```

每个低分项的重构方向用固定格式：

```text
模块/边界 → 结构问题 → 重构动作 → 预期减少的变化放大或认知负荷 → 回归门槛
```

## 最高优先级排序

按**复杂性降低收益**排序：变化放大范围 × 变化频率 × 边界关键性。

没有定位到模块和重构动作的项，不得排进最高优先级——「加强测试」「补文档」这类动作不改变复杂性结构，不能参与这个排序。
