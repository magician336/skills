# 术语表

**变化放大（change amplification）** — 一个小需求迫使多个位置同步修改的现象（Ch 2–3）。

**抽象（abstraction）** — 用较少的概念表达一组细节，使使用者无需了解实现（Ch 4, 7）。

**复杂性（complexity）** — 开发者必须掌握的依赖关系与不明显知识；可表现为变化放大和认知负荷（Ch 2）。

**深模块（deep module）** — 用简单接口隐藏大量实现功能的模块（Ch 4）。

**信息隐藏（information hiding）** — 将设计决策封装在单一模块中，不让其出现在接口或其他模块（Ch 5）。

**信息泄漏（information leakage）** — 同一设计知识被多个模块依赖，导致变化扩散（Ch 5）。

**接口（interface）** — 模块对外可见的用法、约束和语义；它是模块的复杂性成本（Ch 4, 12）。

**类炎（classitis）** — 把“大量小类”误当作好设计，结果增加接口数量和整体复杂性（Ch 4）。

**认知负荷（cognitive load）** — 读者为理解、修改和验证代码必须同时记住的信息量（Ch 2）。

**红旗（red flag）** — 暗示设计可能过度复杂的结构信号，如透传、信息泄漏和重复特殊情况（Ch 1, 8）。

**浅模块（shallow module）** — 接口复杂度接近或超过其隐藏功能的模块（Ch 4）。

**特殊情况（special case）** — 需要额外分支、状态或错误路径才能处理的非正常输入（Ch 8, 10）。

**时间分解（temporal decomposition）** — 按执行先后拆分模块，导致同一知识在多个阶段重复（Ch 5）。

**透传（pass-through）** — 只转发参数或调用、没有隐藏知识的薄层方法/模块（Ch 4, 7）。

**通用模块（general-purpose module）** — 接口服务于一组合理用例，而非只服务当前调用点（Ch 6）。

**战略性编程（strategic programming）** — 为长期降低复杂性而持续投资设计、抽象和重构（Ch 3）。

**战术性编程（tactical programming）** — 只追求当前功能尽快工作，忽略后续复杂性成本（Ch 3）。

**显而易见性（obviousness）** — 读者能从局部代码可靠推断行为、约束和副作用的程度（Ch 18）。
