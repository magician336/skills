# 设计速查

| 看到的信号 | 先问 | 倾向的动作 |
|---|---|---|
| 一个改动要改很多文件 | 哪个知识泄漏了？ | 合并、提取或加深模块 |
| 方法只转发参数 | 这一层隐藏了什么？ | 删除薄层或上移/下移职责 |
| 类很多但每个很小 | 接口成本是否超过隐藏收益？ | 合并成深模块 |
| 大量 `if (特殊状态)` | 能否让正常语义覆盖它？ | 空对象、统一不变量、定义掉错误 |
| 按“先读、再解析、再写”拆类 | 各阶段是否共享格式知识？ | 按知识而非时间重组 |
| 需要新增参数才能复用 | 这是合理通用还是猜测未来？ | 比较至少两个接口，删掉无用选项 |
| 公共 API 难以写评论 | 抽象和职责是否清楚？ | 先写评论，重新设计接口 |
| 代码行为令人意外 | 哪个副作用/默认值不显然？ | 显式命名、局部化状态、补接口评论 |
| 想提前做性能优化 | 有基准和热点证据吗？ | 先测量，保持默认路径简单 |

## 决策规则

1. 能消除的复杂性优先消除；不能消除的才封装。
2. 以接口作为模块成本，以隐藏功能作为模块收益；追求高收益/低成本。
3. 变化会同时影响多个模块时，优先找信息泄漏，而不是逐处打补丁。
4. 只有当错误对上层决策有价值时才暴露；否则屏蔽、聚合或清晰终止。
5. 设计不确定时先做两个候选方案；不要把第一个能工作的方案当作终点。
6. 每次改动都保护已有抽象；若只能局部修复，记录并安排设计改进。
