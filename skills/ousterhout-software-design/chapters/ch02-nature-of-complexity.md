# 第 2 章：复杂性的本质

## 核心思想

复杂性由两部分构成：依赖数量（一个组件改变会牵动多少地方）和不明显程度（读者需要多少额外信息才能推断行为）。它通过变化放大和认知负荷直接降低开发速度。

## 引入的框架

- **变化放大**：一个简单改动需要在许多位置同步修改，说明设计决策没有被集中隐藏。
- **认知负荷**：修改者不得不记住超出当前任务的信息；即使代码行数不多，也可能很复杂。
- **复杂性增量**：每个新特性都可能增加接口、依赖或例外；小增量累积成系统性问题。
  - 何时使用：评估 pull request 或候选架构。
  - 如何做：列出受影响的模块、需要记忆的规则和必须同步的测试。

## 关键概念

- **依赖**：一个模块理解或正确使用另一个模块所需的知识。
- **不明显**：行为不能从局部代码直接推断，必须搜索上下文。
- **红旗**：结构上提示复杂性过高的可观察信号。

## 心智模型

复杂性像“理解税”：每个调用者都要付一次。把一项知识集中到单模块，能让所有调用者共同节省成本。

## 反模式

- **以行数衡量简单**：短函数可能依赖许多隐藏约定。
- **分散补丁**：逐处处理变化放大而不改变知识归属。

## 工作示例

一个 API 的分页规则分散在控制器、服务和客户端。将规则集中到服务接口并在评论中写明边界后，客户端不再需要知道内部页码转换；一次规则变化只改服务模块。

## 关键结论

1. 评审时同时检查依赖和不明显程度。
2. 任何重复的设计知识都是潜在变化放大。
3. 优先降低调用者的认知负荷，而不是只减少实现代码。
