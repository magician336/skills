# 第 14 章：选择的名字

## 核心思想

名字是开发者每天读取的接口。精确、一致、能表达抽象层级的名字会降低认知负荷；含糊、缩写和同义混用会制造隐藏依赖。

## 引入的框架

- **精确命名**：名称应表达对象的真实语义和范围，而不是实现偶然性。
- **一致命名**：同一概念始终使用同一词；不同概念不要共享一个泛名。
- **抽象层级命名**：高层 API 使用目标语义，低层实现使用机制语义。
  - 何时使用：公共类型、方法、字段和错误码命名时。
  - 如何做：写出调用者会如何理解名字，检查是否需要额外搜索才能确认含义。

## 关键概念

- **语义密度**：名字在少量字符中传达的有效信息。
- **误导性名字**：让读者形成错误行为预期的名称。
- **命名约定**：团队共享的词汇、大小写和动词规则。

## 心智模型

名字是免费的文档入口；每次调用都会重复读取它。一个准确名字能在整个代码库持续节省解释成本。

## 反模式

- **万能词**：`data`、`manager`、`handle` 在没有限定语义时隐藏职责。
- **同物异名**：`remove`、`delete`、`drop` 实际表示同一行为，却让调用者猜差异。

## 工作示例

如果方法实际返回“缓存中是否存在并更新访问时间”，命名为 `get` 会误导调用者；`lookupAndTouch` 或更高层的 `fetch` 才能表达语义。若团队统一使用 `fetch` 表示可能触发加载，应在约定中固定它。

## 关键结论

1. 名字应表达行为和抽象，而非内部字段。
2. 先统一词汇，再决定局部命名。
3. 发现名字需要长篇解释时，重新检查设计边界。
