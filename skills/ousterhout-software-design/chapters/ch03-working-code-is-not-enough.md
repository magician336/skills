# 第 3 章：工作代码是不够的

## 核心思想

能运行的代码只是起点。战术性编程追求眼前功能，容易留下浅接口和重复知识；战略性编程持续投入设计，让后续功能更便宜、更稳定。

## 引入的框架

- **战术性编程 vs. 战略性编程**：前者最小化当前改动，后者把一部分时间用于通用抽象、重构和接口质量。
  - 何时使用：需求压力要求“先能跑”时。
  - 如何做：先保证行为，再检查设计红旗；为高频路径预留重构预算。
- **设计投资回报**：早期多花的设计时间，会在多个未来功能中摊薄。

## 关键概念

- **战术债**：为了短期速度引入、却会在以后反复支付的复杂性。
- **重构窗口**：在功能迭代之间主动改善边界的时间。
- **战略抽象**：由多种已知用例共同支持、而非为单个调用点定制的接口。

## 心智模型

把代码库看成需要维护的基础设施：每次只在旧路面上打补丁，最终所有交通都会变慢；适度重建路段能提升整体吞吐。

## 反模式

- **“以后再重构”**：没有明确窗口和范围，复杂性会先扩散。
- **过早抽象**：没有足够用例就猜测未来，制造无效通用性。

## 工作示例

实现缓存功能时，直接在三个调用点加入不同的 key 拼接逻辑属于战术方案。战略方案先定义缓存模块的职责和 key 规则，再让三个调用点共享它；实现可能多写一个模块，但下一个缓存后端只需修改一处。

## 关键结论

1. 把设计质量作为交付的一部分。
2. 先工作、再设计评审，不要把“可运行”误作“可演化”。
3. 用实际用例验证抽象，避免为未知未来堆参数。
