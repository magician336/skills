# 第 4 章：模块应该是深的

## 核心思想

模块的收益是它提供的功能，成本是接口给系统增加的复杂性。深模块用简单接口隐藏大量实现；浅模块暴露的接口接近其实现，几乎没有降低认知负荷。

## 引入的框架

- **深度 = 功能收益 / 接口成本**：接口越小、隐藏功能越多，模块越深。
  - 何时使用：比较类、服务或库的候选边界。
  - 如何做：列出调用者必须知道的内容，再问哪些能移入实现；让常见路径拥有默认行为。
- **类炎（classitis）**：机械地把大类拆成许多小类，接口数量上升而隐藏收益下降。
- **默认常见用例**：少数特殊选项不应污染大多数调用者的入口。

## 关键概念

- **深接口**：短而稳定，但背后处理大量机制。
- **浅接口**：方法多、参数多，却只包装几行实现。
- **透传方法**：新增调用层次却没有隐藏知识。

## 心智模型

Unix 文件 I/O 以少数系统调用隐藏文件系统、权限、缓存和设备差异；这比为每个内部机制提供单独类更深。

## 反模式

- **“每个类都必须很小”**：把行数规则置于接口收益之上。
- **无价值包装**：公共方法只写入字段或转调同名方法。

## 工作示例

Java 文件读取常需显式创建多个流对象；若绝大多数调用都需要缓冲，缓冲应成为默认能力，关闭它才是隔离选项。接口因此更深，常见代码也更短。

## 关键结论

1. 不要以类或方法行数单独判断设计质量。
2. 删除没有抽象收益的薄层。
3. 把复杂机制放入少数深模块，给常见用例简单入口。
