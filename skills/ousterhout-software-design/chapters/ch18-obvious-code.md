# 第 18 章：代码应该是显而易见的

## 核心思想

显而易见的代码让读者从局部即可预测行为、状态变化和副作用。隐藏控制流、模糊名字、过度间接和不一致约定会迫使读者搜索上下文，增加复杂性。

## 引入的框架

- **可推断性**：读者无需查看大量其他模块就能解释当前代码。
- **减少惊讶**：默认值、生命周期、缓存和错误行为应符合名称和常规预期。
- **显式胜过魔法**：关键副作用和跨层转换应在接口或评论中可见。
  - 何时使用：评审可读性、重命名或引入框架时。
  - 如何做：让数据流短而一致，集中副作用，使用精确名字和非显然评论。

## 关键概念

- **惊讶**：代码实际行为与读者由名称/结构形成的预期不一致。
- **局部推理**：在少量上下文内验证正确性。
- **可见副作用**：调用会改变状态、缓存、线程或外部系统的事实。

## 心智模型

代码阅读像预测程序：每个额外的隐藏状态都是需要在脑中维护的变量。显然性就是减少这些隐变量。

## 反模式

- **魔法回调/全局状态**：调用点看不出控制流和副作用。
- **过度间接**：为了“可扩展”引入多层工厂、代理和反射。

## 工作示例

一个名为 `save` 的方法同时写数据库、刷新缓存并发送事件，会让调用者产生错误预期。拆出明确的协调层，或在接口评论中显式说明副作用，能让调用路径可推断。

## 关键结论

1. 让名称、层次和实际行为一致。
2. 把重要副作用集中并暴露在合适抽象层。
3. 复杂机制可隐藏，但不能让关键语义变成魔法。
