# 第 16 章：修改现有的代码

## 核心思想

修改旧代码时，最容易把局部需求变成新的复杂性。先理解现有抽象和红旗，再选择保持边界、局部重构或提取深模块的路径。

## 引入的框架

- **先读后改**：沿调用路径、接口评论和测试理解设计意图，再修改。
- **设计保持**：新功能应复用并强化现有抽象，避免绕过接口直接访问内部状态。
- **改动即重构机会**：若当前位置已经存在信息泄漏或透传，顺手消除会降低后续成本。
  - 何时使用：遗留系统、紧急修复、跨团队代码。
  - 如何做：建立行为基线，识别受影响依赖，小步迁移并在每步验证。

## 关键概念

- **局部修复**：最小行为改变，但可能保留设计债。
- **结构性改进**：改变知识归属，减少未来变化扩散。
- **回归面**：改动可能影响的调用者、错误语义和性能路径。

## 心智模型

把旧代码视为带历史约束的系统：先恢复它的模型，再决定哪些约束仍有价值，不能只按表面代码重写。

## 反模式

- **旁路接口**：为了赶进度直接读写内部字段。
- **无基线重构**：行为、性能和错误语义同时改变，无法定位回归。

## 工作示例

给旧解析器增加压缩格式支持时，先锁定现有输入输出和异常行为；若格式知识分散在调用者，先集中解析接口，再加入压缩实现。每步保留兼容测试，避免“一次性大改”。

## 关键结论

1. 先建立行为和性能基线。
2. 新代码优先使用现有深接口；若接口浅，记录并改善它。
3. 用小步迁移控制回归面，同时减少设计债。
