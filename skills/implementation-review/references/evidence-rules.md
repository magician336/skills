# 证据规则：状态口径与有效性检查

## 状态词表

判定层只有四个值：

| 状态 | 含义 | 是否阻塞 |
| --- | --- | --- |
| `PASS` | 当前 head 有可复核证据，满足本次交付要求 | 否 |
| `FAIL` | 跑过且不满足要求 | 是 |
| `NOT RUN` | 没跑，且没有承接它的解除条件载体 | 是（当前范围内） |
| `DEFERRED_MANUAL` | 需人工执行的验证尚未完成，代码侧条件已满足，且有跟进载体与写明的解除条件 | 不阻塞代码合并，阻塞最终放行 |

放行层例外词：`N/A`（前提不存在）、`WARNING`（环境限制但等价路径已通过）、`PASS (follow-up)`（本次接受不阻塞，但真实服务验收须链接独立 issue）。这三个词不写进判定矩阵——`PASS (follow-up)` 写进去会让读的人分不清它是「通过」还是「没做」。

`DEFERRED_MANUAL` 的三条硬要求，缺任一项即无效：① 代码侧条件已满足；② 写明解除条件；③ 有跟进载体（issue 编号或明确负责人 + 期限）。

## 当前 head 原则

证据必须来自当前 head。旧 head 上跑绿的结果不构成当前 head 的证据。

常见违规形态：

- PR 描述里引用的是上一次 push 的 CI 链接；
- 矩阵行标 `PASS`，但证据命令跑的是改动前的 commit；
- 合并基线后代码变了，测试没重跑，证据被沿用。

发现这类情况 → 该行标 `NOT RUN`，并在发现里写明证据指向的 commit 与当前 head 的差异。

## 「跳过」不等于「通过」

CI 中 skipped 的步骤等于 `NOT RUN`。被跳过的检查必须带可解释理由（测的什么面、为什么是这个面、依据哪个基线）。把跳过写进证据栏等于没有证据。

## 证据有效性检查清单

评审 agent 产出时逐条查。这些检查针对的是「证据看起来在、实际上钉不住」的情况。

### 1. 替身是否遮蔽了生产代码

问三件事：

- 替身（fake / stub / mock / test double）**是不是自己实现了这个行为**——自己置字段、自己算结果、自己填标记？
- 断言读的是**替身返回的对象**，还是**生产链路的输出**（HTTP 接缝的响应、DB 往返、真实端口）？
- 替身有没有**绕过**生产代码的那一段？

任一为「是」⇒ 该断言钉的是替身，不是生产行为。典型信号：断言信息写着「must be persisted, not dropped」，但替身的 getter 返回同一指针、setter 是 `return nil` 空实现，而服务层是就地改内存——删掉整行持久化调用，测试照样绿。

### 2. 反向变异是否转红

挑 1–2 个关键断言临时改坏生产代码，确认测试转红，然后立刻还原。

- 变异后仍全绿 ⇒ 该断言无效（不是「测试写得宽松」，是「测试没测到」）。
- 变异后转红 ⇒ 证据有效。

这一步是唯一能证明「测试真的钉在生产代码上」的方法，其余都只是推断。

### 3. 断言方向

断言读的是替身仓库的内部 map（`repo.rows[...]`）而不是重新读库时，它测的是替身的内存状态。服务层就地修改同一个对象时，断言读的是**被就地改过的对象**——结构上不可能失败。

修法：替身的 setter 真落库、getter 返回副本，或补一条真实 DB 往返用例。

### 4. 接缝真实性

跨模块、持久化、权限、并发、审计的改动必须证明真实的 application / HTTP seam 与事务行为。以下都不能替代：

- 直接调 store / 内存替身的单元测试；
- 「CI 是绿的」这种通用结论；
- 只跑了编译。

要能指出：请求从哪进、事务在哪开、失败时是否零写入、权限在哪判、审计写到哪、从哪个 seam 读回。

### 5. 术语一致

代码、迁移、接口契约、测试名、PR 描述用同一套术语。术语冲突说明契约没定，不是文档问题——按 `Required` 报。

## 严重级别与判级

- `Blocker`：违反规格、事务 / 权限 / 数据一致性、缺当前 head 证据，或证据无效（钉不住生产代码）；
- `Required`：本轮应补齐的契约、测试或文档同步；
- `Suggestion`：记录为后续事项，不阻塞。

## 两轮规则

同一类问题连续两轮修完又冒新 `Blocker`，说明目的地切得太大或契约没定。停止继续打补丁，回到计划评审重新切分目的地或拆片；继续打补丁只会让每轮都更接近一个错误的形状。
